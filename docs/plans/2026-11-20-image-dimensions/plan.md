## 背景・目的

画像のある日記を開くと、画像が読み込まれるまで画像の寸法が分からない。文章は画像を避けて組むので、まず画像なしで組まれ、画像の読み込みが終わった時点で組み直される。読んでいる最中に文章の位置が動く。

画像の幅と高さをあらかじめ DB に持っておき、表示の最初から画像の場所を空けて文章を組む。すでにアップロード済みの画像には寸法がないので、寸法を記録する一括パッチのスクリプトを用意する。このスクリプトは、新しいアップロードと同じ基準での再圧縮も行い、圧縮の導入前に保存された重い画像を軽くする。

## 方針

### 寸法の定義（確定済み。変更しない）

- 保存する寸法は、**ブラウザが画像を表示するときの幅と高さ（px）**。EXIF の向きを反映した値で、`<img>` の `naturalWidth` / `naturalHeight` と一致する
- 幅と高さは、両方そろっているか、両方 NULL かのどちらか。片方だけの状態を作らない
- 値は 1 以上 100000 以下の整数

### 新しいアップロードの仕様

**ブラウザ**

- `compressImageForUpload` の戻り値を、送る File だけから「送る File と、その画像の寸法（幅・高さ、または取れなかったことを示す null）」に変える
- 寸法は、実際に送るファイルの表示寸法にする
  - 圧縮後の画像を送るとき: 圧縮後の幅と高さ
  - デコードはできたが元のファイルを送るとき（軽くならなかった、10MB を超えた等）: 元の画像の、向きを反映した幅と高さ
  - 圧縮しない画像（GIF、アニメーション WebP、APNG、アニメーションの判定ができなかったもの）: 寸法を知るためだけにデコードを試み、取れたらその値、取れなければ null
  - デコードに失敗したとき: null
- 寸法が取れなくても、アップロードは今までどおり続ける。寸法の取得のために、圧縮の採用・不採用の判断（どのファイルを送るか）を変えない
- アップロードの FormData に、寸法があるときだけ `width` と `height` を足す

**サーバー（`POST /api/diaries/:id/image`）**

- `width` と `height` を受け取る。両方が「1 以上 100000 以下の整数を表す 10 進の文字列」のときだけ採用する。どちらかが無い、または形式が合わないときは、両方を NULL として保存し、アップロード自体は成功させる（寸法が無くても表示はできるため、寸法の不備で画像を断らない）
- 画像キーと寸法は、同じ 1 回の更新で保存する
- 応答の JSON に `image_width` と `image_height` を足す（`image_key` は今までどおり）
- サーバーは画像の中身から寸法を読まない。送られた値は、ログイン済みの本人のブラウザが測った値として扱う
- `DELETE /api/diaries/:id/image` は、画像キーと一緒に寸法も NULL にする
- 日記の JSON を返す既存の API（`app/routes/api/diaries/[id].ts`）で、画像の項目（`image_scale` など）を返している箇所には、`image_width` と `image_height` も足す。日記を更新する API（PUT）からは寸法を変更できないようにする

**公開**

- `publishDiary` は、`image_width` と `image_height` を他の画像項目と同じようにスナップショットへ写す
- 公開ページ（`app/routes/d/[id].tsx`）は、スナップショットの寸法を使う

### 表示の仕様

- `FlowText` に、画像の寸法を受け取る省略可能な props を足す。`DiaryScrollFrame` はそれをそのまま渡す
- `FlowText` が配置の計算に使う寸法は次の順で決める
  1. いま表示している画像の読み込みが終わっていれば、その実寸（今までと同じ）
  2. まだなら、props で渡された寸法
  3. どちらも無ければ、今までどおり画像なしで組み、読み込み後に組み直す
- 読み込み後の実寸が props の寸法と違っていたら、実寸に合わせて組み直す（保存された寸法が間違っていても、最終的な表示は今までと同じになる）
- props の寸法は「いま表示している画像」の寸法でなければならない。編集画面では、画像を選び直した直後はプレビュー（選んだ画像）を表示するので、その間はプレビューの画像の寸法を渡す。アップロードが失敗してプレビューを取り消したら、保存済みの画像の寸法に戻す。合わない寸法を渡すくらいなら、寸法なし（null）を渡す
- この値の選び方は、props と state から render 中に導出する。Effect で state を同期しない（CLAUDE.md の「Effect の使い方」に従う）
- 公開ページは、スナップショットの寸法を渡す。編集画面は、日記の寸法を初期値として渡す

### 一括パッチのスクリプトの仕様

**置き場所と起動**

- `scripts/backfill-images.mjs`。`node scripts/backfill-images.mjs [--local] [--apply]` で起動する。`package.json` の scripts に `images:backfill`（`node scripts/backfill-images.mjs`）を足す
- `--local` を付けるとローカルの D1・R2、付けなければ本番（リモート）を対象にする（`scripts/upload-fonts.sh` と同じ流儀）
- **`--apply` を付けないときは確認だけ**を行い、D1 と R2 を一切書き換えない。対象の画像ごとに、現在の形式・寸法・バイト数と、実行した場合の結果（差し替えるか、寸法だけ記録するか、差し替え後の形式・寸法・バイト数）を一覧で出す。確認だけの実行でも、R2 から画像を読み、手元で圧縮を試す（読み取りだけ）
- D1 のデータベース名と R2 のバケット名は、`wrangler.toml` から読む。起動時に `scripts/check-wrangler-config.mjs` と同じ確認（本番が対象のときは `--deploy` 相当）を行い、設定が足りなければ始めない
- D1 と R2 へのアクセスは wrangler の CLI（`wrangler d1 execute ... --json`、`wrangler r2 object get / put / delete`）で行う。API トークンなどの秘密情報をスクリプトが読んだり表示したりしない
- wrangler を呼ぶ部分は差し替えられる作りにする（`--apply` の 1 枚ごとの手順を、wrangler を実際に呼ばずにユニットテストで確かめるため。下の「`--apply` のときの 1 枚ごとの手順」を参照）
- 画像の処理には `sharp` を使う（devDependencies。本番のバンドルには入らない）

**対象**

- `diaries` と `diary_snapshots` のうち、`image_key` があり、寸法（`image_width` または `image_height`）が NULL の行が参照している画像キー。同じキーは 1 回だけ処理する
- キーが `diaries/<英数字・ハイフン・アンダースコア>/<英数字・ドット・ハイフン・アンダースコア>` の形でないものは、処理せずに警告して飛ばす（SQL やコマンドに安全に埋め込めるキーだけを扱う）
- R2 に実体がないキー、画像として読めないものは、処理せずに警告して飛ばし、残りを続ける

**1 枚ごとの判断（新しいアップロードと同じ基準）**

- 表示寸法は、EXIF の向きを反映した幅と高さ
- アニメーションの判定は、ブラウザ側の `detectAnimation`（`app/lib/image-compress.ts`）と同じ規則にする: PNG は最初の `IDAT` より前に `acTL` チャンクがあればアニメーション、WebP は `VP8X` のアニメーションのフラグで判定し、GIF は常に変換しない。`sharp` のフレーム数（`metadata.pages`）は APNG を数えないので、それだけでアニメーションを判定しない
- GIF、アニメーションと判定したもの（アニメーション WebP・APNG）、判定できなかったもの（`unknown`）は変換しない。寸法だけ記録する
- それ以外は、向きを反映したうえで、長辺が 2000px を超えていれば長辺 2000px に縮め（縦横比を保ち、拡大しない）、JPEG は JPEG（品質 85）、PNG と WebP は WebP（品質 85）に書き出す
- 書き出した結果を採用するかは、ブラウザの圧縮と同じ規則で決める: 縮小した場合は、10MB 以下なら元より大きくても採用する。縮小していない場合は、元より小さいときだけ採用する。10MB を超える結果は採用しない
- 採用しないときは、元の画像を残し、寸法だけ記録する
- 長辺・品質・10MB の値は `app/lib/constants.ts` と同じ値を使う。判断（アニメーションの判定、縮小後の寸法、出力形式、採用するか）は純粋関数として `scripts/lib/image-backfill.mjs` に置き、`app/lib/image-compress.ts` の対応する関数（`detectAnimation`、`computeResizedSize`、`chooseOutputType`、`chooseUploadSource`）および `app/lib/constants.ts` の値と同じ結果になることを、ユニットテストで突き合わせる（片方だけ変えたらテストが落ちる）。アニメーションの判定は、APNG、静止画の PNG、アニメーション WebP、静止画の WebP、GIF、途中で切れたバイト列を含む同じ入力で、`detectAnimation` と同じ結果になることを確かめる。そのために `vitest.config.ts` の `include` に `scripts/**/*.test.mjs` を足してよい
- 出力形式の突き合わせ: ブラウザは WebP で書き出せないときだけ PNG にするが、これはブラウザの書き出しの都合で、`chooseOutputType` の結果（PNG と WebP は WebP）には含まれない。スクリプトは常に `chooseOutputType` と同じ形式（JPEG は JPEG、PNG と WebP は WebP）で書き出し、PNG への切り替えは持たない。テストの突き合わせの対象は `chooseOutputType` の結果とする

**`--apply` のときの 1 枚ごとの手順（この順で）**

1. 差し替える場合: 新しいキー（元のキーと同じ `diaries/<日記 ID>/` の下に、新規アップロードと同じ形の新しいファイル名。拡張子は書き出した形式に合わせる）で R2 に保存する。Content-Type は書き出した形式に合わせる
2. D1 を更新する。`diaries` と `diary_snapshots` の両方で、`image_key` が元のキーの行について、差し替える場合は `image_key` を新しいキーにし、寸法を入れる。寸法だけ記録する場合は寸法だけ入れる。`updated_at` などほかの列は変えない。`diaries` と `diary_snapshots` の更新は、片方だけ成功することがありうる
3. 差し替えた場合で、D1 の更新がすべて成功したとき: 「これから消す古いキー」を標準出力に出し（削除の前に出すので、D1 の更新の直後に止まっても記録が残る）、古いキーの参照が `diaries` と `diary_snapshots` の両方で 0 件だと確かめてから、古いオブジェクトを削除する。参照が残っている、確かめられない、削除に失敗した、のどれかなら、古いオブジェクトを残して「R2 に残ったキー」として報告する
4. D1 の更新が失敗したとき（片方のテーブルだけ成功したとき、結果が分からないときを含む）:
   - 古いオブジェクトは消さない
   - 新しく保存したオブジェクトは、新しいキーの参照が両テーブルで 0 件だと確かめられたときだけ消す。参照がある（片方のテーブルが新しいキーに変わっている）、または確かめられないときは、消さずに残し、「R2 に残ったキー」として報告する。削除に失敗したときも同じく報告する
   - その画像は失敗として報告する
   - 再実行での回復: 元のキーを参照していて寸法が NULL の行が残っていれば、再実行でその元のキーがもう一度処理される（残っている行が新しいキーと寸法に更新され、そのあと元のキーの参照が 0 件になっていれば元のオブジェクトが消える）。この場合、`diaries` とスナップショットが別々の新しいキーを指すことがあるが、どちらも同じ内容の画像で、表示に問題はない

- R2 のオブジェクトを消してよい条件: **D1 から参照されている可能性があるオブジェクトは消さない。** スクリプトが R2 のオブジェクトを消すのは、消す直前に D1 へ問い合わせて、`diaries` と `diary_snapshots` のどちらにも、そのキーを `image_key` に持つ行が 0 件だと確かめられたときだけにする。問い合わせに失敗した、または 1 件でも参照があったときは、消さずに残し、キーを報告する。これは古い画像にも、新しく保存した画像にも同じように当てはめる
- 既存のキーに上書きしない。画像の URL は 1 年のキャッシュ（immutable）で配信されるため、中身を変えるときは必ず新しいキーにする
- どの段階で失敗しても、表示中の画像が失われない順序にする（新しい画像を保存してから DB を変え、DB が変わって古いキーの参照が 0 件だと確かめてから古い画像を消す）。失敗した画像はエラーとして報告し、残りを続ける
- 古いオブジェクトを残したとき（参照が残っていた・確かめられなかった・削除に失敗した）、および D1 の更新後・削除前に止まったときは、古いオブジェクトが R2 に残る。参照されているものは表示に使われているので残すのが正しく、参照されていないものは残っても表示には影響しない
- 再実行で回復できるのは、寸法の記録と差し替え（新しい画像の保存と D1 の更新）まで。途中で止まっても、もう一度実行すれば、D1 の更新が終わっていない行を処理できる（寸法が入った行は対象から外れる。片方のテーブルだけ更新された場合は上の 4 のとおり）。D1 の更新がすべて終わった画像は次回の対象から外れるので、**そのあとの古い画像の削除は再実行ではやり直されない**。処理が終わった状態でもう一度実行すると、対象は 0 件になる
- 最後に、処理した件数（差し替え・寸法だけ・飛ばした・失敗）と、差し替え前後の合計バイト数を出す。R2 に残ったキー（参照が残っていた・確かめられなかった・削除に失敗した）があれば一覧にし、手で消す前に参照がないことを確かめるよう添えて、手で消すためのコマンド（`wrangler r2 object delete <バケット名>/<キー>` に、対象に合わせて `--local` または `--remote` を付けたもの）を示す。失敗が 1 件でもあるとき、または R2 に残ったキーが 1 件でもあるときは、終了コードを 0 以外にする
- 手順（`docs/deploy/README.md`）には、R2 に残ったキーが出たときの対処（手で消す前に、`diaries` と `diary_snapshots` のどちらにもそのキーを `image_key` に持つ行がないことを確かめ、示されたコマンドで消す。参照されていないものは、残しても表示には影響しない）を含める
- 1 枚ごとの手順は、wrangler の呼び出しを差し替えたユニットテストで次を確かめる
  1. 順序が「保存 → D1 更新 → 古いキーの参照の確認 → 古い画像の削除」であること
  2. 確認だけの実行では、書き込みのコマンド（put、delete、UPDATE）が 1 回も呼ばれないこと
  3. 古い画像の削除が失敗したとき、そのキーが報告され、終了コードが 0 以外になり、残りの画像の処理が続くこと
  4. D1 の更新が全部失敗したとき、古い画像を消さず、新しいキーの参照が 0 件と確かめたうえで新しいオブジェクトを消すこと
  5. D1 の更新が片方のテーブルだけ成功したとき、古い画像も新しい画像も消さないこと。そのあとの再実行で、残った行が処理され、参照がなくなった元のオブジェクトが消えること
  6. 参照の確認の問い合わせが失敗したとき、どのオブジェクトも消さないこと

### 設計

- 寸法を DB の列として持つのは、既存の画像項目（`image_scale`、`image_rotation`）と同じ持ち方にそろえるため。公開スナップショットは公開時点の画像を指すので、スナップショットにも同じ列を持つ
- 寸法をブラウザから送るのは、圧縮のために画像をデコードした時点で分かっているため。サーバーに画像を解析する処理を足さずに済む
- 一括パッチを手元のスクリプトにするのは、アプリの画面や API を増やさずに済むため。ブラウザの圧縮とバイト列は一致しないが、基準（長辺・品質・形式・採用の規則）はそろえる

### 動作確認

- 受け入れ基準のうち、ユニットテストでは確かめられないものを、画面とローカルの D1・R2 で確かめる
- 役割分担: 実装担当は、実装・ユニットテスト・4 つの検証コマンド・commit までを行う。画面とスクリプトの動作確認は、采配役が検収のときに行う（実装担当が自分で確かめた範囲があれば、何をどこまで確かめたかを報告に書く）。実装担当は本番（リモート）の D1・R2 に対してコマンドを実行しない
- 動作確認には、検証対象の worktree から起動した dev サーバーと、その worktree のローカルの D1・R2 だけを使う。手順と確かめる内容は request.md の「検証と報告」に書く

## 未確定事項・リスクと判断の委ね方

| 項目 | 内容 | 実装時の扱い |
|---|---|---|
| 圧縮しない画像の寸法の取り方 | GIF などは今はデコードしていない | 寸法を知るためのデコードの方法（`createImageBitmap`、`Image` 要素など）は担当が判断してよい。失敗したら null。送るファイルの選択を変えないこと |
| `FlowText` の中での寸法の持ち方 | props と読み込み後の実寸の扱い、画像を差し替えたときの古い実寸の捨て方 | 担当が判断してよい。上の「表示の仕様」の優先順位と、Effect を使わない方針を守ること |
| 編集画面での寸法の受け渡し | プレビュー中の寸法と保存済みの寸法の持ち方、コールバックの形 | 担当が判断してよい。表示している画像と寸法が食い違わないこと |
| `wrangler d1 execute` で複数の文を送ったときの原子性 | `diaries` と `diary_snapshots` の更新が片方だけ成功する可能性 | R2 のオブジェクトは、消す直前に D1 で参照が 0 件と確かめたものだけ消す（古い画像も、新しく保存した画像も）。片方だけ成功しても、参照されている画像は残るので表示は壊れない（このとき古い画像も新しい画像も消さず、その画像を失敗として報告する）。再実行で残りの行が処理され、参照がなくなった元のオブジェクトが消えること。原子的にできる方法があればそうしてよい |
| `sharp` の導入 | pnpm が依存のビルドスクリプトを既定で実行しない | 事前ビルド済みのバイナリで動くことを確かめる。動かすために pnpm の設定変更が要る場合は、最小の設定にとどめ、報告に書く |
| ローカルの R2 の場所 | dev サーバーと wrangler の `--local` が同じ保存場所を見るか | 動作確認で確かめる。食い違う場合は、スクリプト側で合わせる方法を担当が判断し、手順に書く |
| 本番での動作 | スクリプトの本番（リモート）での実行は確かめられない | ローカルで確かめ、リモートは wrangler の同じコマンドの `--remote` に切り替わることをコードで確かめる。本番へは実行しない |
| 実行中の編集 | スクリプトの実行中に画像を差し替えると、その行の更新が空振りし、保存した新しい画像が使われずに残る | 手順に「実行中は日記を編集しない」と書く。対策のための仕組みは足さない |
| 既存の scripts との名前の持ち方の違い | 既存のマイグレーション用 scripts はデータベース名を直に書いている | 今回は変えない。スクリプトは `wrangler.toml` から読む |
| 関数名・ファイル内の分割・テストの書き方 | 実装の詳細 | 担当が判断してよい |
| 止まって報告する条件 | 寸法の定義、アップロードの仕様、圧縮の基準、スクリプトの既定（確認だけ）と手順の順序の変更、`sharp` 以外の依存の追加、CSP の変更、本番のデータへのアクセスが必要になったとき | 変更・実行せず、選択肢と推奨を報告して止まる |

## 公開経路

作業ブランチ `plan/2026-11-20-image-dimensions` に commit する。検収の合格後、采配役が push し、main への PR を作る。main への統合は PR 経由（必須チェックは CI の `ci` ジョブ）で、マージは利用者が行う。本番への反映は、利用者が手元で `pnpm run deploy` を実行する（マイグレーションはデプロイのコマンドの中で適用される）。一括パッチは、デプロイのあとで利用者が手元で実行する。自動デプロイはない。
